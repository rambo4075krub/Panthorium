  3. รู้จักคนใหม่ → คุยอย่างสมัครใจ: ยืนยันคุณสมบัติผู้ใหญ่ → เปิดโปรไฟล์ Connect → กำหนดสิ่งที่สนใจและความเป็นส่วนตัว → ทั้งสองฝ่ายสนใจตรงกัน → แชท → ส่งคำเชิญโทร → ผู้รับรับสาย → กล้องยังปิดจนเจ้าของอุปกรณ์เลือกเปิด → จบสายและให้เลือกบล็อก/รายงาน
  4. เรียนร่วมกัน: กลุ่มเรียนที่มีสมาชิกชัดเจน → คลิปในกลุ่ม → คำถามอ้างอิงเวลาของคลิป → ห้องแชทกลุ่ม → โทรตามสิทธิ์กลุ่ม โดยผู้เยาว์ไม่ถูกค้นพบผ่าน Connect และไม่มีผู้ใหญ่แปลกหน้าติดต่อโดยอาศัยชื่อโรงเรียน

การ “แชร์” หมายถึงสร้างการอ้างอิงที่ตรวจสิทธิ์ใหม่เมื่อเปิด ไม่ใช่คัดลอกไฟล์ส่วนตัวให้เป็นสาธารณะ หากผู้รับไม่มีสิทธิ์ ให้แจ้งว่าเปิดไม่ได้โดยไม่เผยชื่อ ภาพตัวอย่าง หรือข้อความส่วนตัว ไม่ขยายสิทธิ์ให้เอง

3. เสียงเป็นหลัก แต่การตัดสินใจต้องชัดเจน
คำสั่งตัวอย่างสิ่งที่ระบบทำจุดยืนยัน
“เปิดคลิปที่ฉันดูค้างไว้”เปิดรายการที่มีสิทธิ์และตำแหน่งล่าสุด อ่านชื่อสั้น ๆไม่ต้องยืนยันเพิ่มสำหรับการเปิดอ่าน
“ส่งคลิปนี้ให้นิด ตรงนาทีที่สอง”ระบุผู้รับจากรายชื่อจริง ถ้าชื่อซ้ำให้เลือก ตรวจสิทธิ์คลิป สร้างข้อความแนบเวลาอ่านผู้รับ บริบทห้อง และสิ่งที่ส่งก่อนส่งจริง
“โพสต์รูปนี้ให้เฉพาะเพื่อน”สร้างร่างพร้อมผู้ชม ตรวจว่าเป็นภาพที่เลือกจริงยืนยันภาพ คำบรรยาย และผู้ชมก่อนเผยแพร่
“โทรหาแพรว”ตรวจบุคคล บริบทที่อนุญาต และเวลาห้ามรบกวนผู้โทรยืนยันผู้รับ; ผู้รับรับสายเอง; ไม่เปิดกล้องอัตโนมัติ
“เริ่มไลฟ์ขายแก้วรุ่นนี้”เปิดห้องเตรียมพร้อม แสดงสินค้า ผู้ชม อุปกรณ์ การเก็บย้อนหลังยืนยันเริ่มออกอากาศ ไม่เปลี่ยนจากพรีวิวเป็นสาธารณะเพราะคำสั่งกำกวม

โหมดส่วนตัวใช้ข้อความแจ้งเตือนทั่วไป ไม่อ่านชื่อคู่สนทนาหาคู่หรือข้อความส่วนตัวออกลำโพงโดยอัตโนมัติ รองรับหูฟัง ปุ่มเงียบ คำบรรยาย และข้อความแทนเสียง ผู้ใช้แว่นหรืออุปกรณ์ไร้จอใช้ action contract เดียวกัน มีผู้รับ เป้าหมาย ผู้ชม การยืนยัน และผลลัพธ์ที่ย้อนตรวจได้

AI ช่วยร่างคำบรรยาย สรุปคลิปสาธารณะ ตัดไฮไลต์ สร้าง alt text และแปลภาษาได้ตามสิทธิ์ สำหรับข้อความหรือสายส่วนตัวต้องมีขอบเขตการยินยอมแยก ไม่ส่งบทสนทนาของคนอื่นเข้า Gemini หรือความจำ AI ส่วนบุคคลโดยปริยาย ไม่รับประกันว่า AI ตรวจจับเนื้อหาไม่เหมาะสมได้ทั้งหมด

ตัวควบคุมไมโครโฟนกลาง: เมื่อเริ่มสาย Talk/Connect หรือเปิดกล้องถ่ายทอดสด ต้องพัก wake-word, ASR, เส้นทางไมค์ Gemini และการถอดเสียงเบื้องหลังของ Sentinel โดยปริยาย แสดงว่าแอปใดกำลังใช้ไมค์ ห้ามให้สองโมดูลรับเสียงเดียวกันโดยไม่ตั้งใจ เมื่อจบสายหยุด track ของสาย และให้ผู้ใช้ยืนยันก่อนกลับไปฟังต่อใน AI ผู้ใช้ยังควบคุมวางสาย/ปิดไมค์ด้วยปุ่มได้ทันที

หากต้องสั่ง AI ระหว่างสาย ให้มีปุ่มกดเพื่อสั่งที่ผู้ใช้ตั้งใจเรียก พักการส่งไมค์เข้าห้องในช่วงนั้น แสดงขอบเขตเสียงที่จะส่ง และไม่ส่งเสียงคู่สนทนาเข้า AI; บนอุปกรณ์ที่ทำ audio routing นี้ไม่ได้ ให้ใช้ปุ่มควบคุมสายแทน ไม่อ้างว่าพัก AI แล้วแต่ยังฟังทุกคำอยู่

4. บัญชีเดียว แต่มีขอบเขตตัวตน 4 แบบ
บริบทสิ่งที่แสดงสิ่งที่ไม่เชื่อมโดยอัตโนมัติ
บุคคล/ผู้สร้างชื่อแสดง นามแฝง รูปประจำตัว ช่อง ผลงาน และผู้ชมที่เลือกอีเมลล็อกอิน เบอร์โทร เอกสารยืนยัน วันเกิดเต็ม และไฟล์ส่วนตัว
องค์กร/โรงเรียนข้อมูลตามสมาชิกองค์กร ทีม และทรัพยากรที่อนุญาตโพสต์ส่วนตัว แชทส่วนตัว ประวัติซื้อและโปรไฟล์หาคู่; ตำแหน่งผู้บริหารไม่ให้สิทธิ์อ่านข้อมูลเหล่านี้
ร้านค้าชื่อร้าน ข้อมูลผู้ขายที่ต้องเปิดเผย สินค้า ช่องทางบริการและเงื่อนไขที่อยู่ลูกค้าต่อพนักงานที่ไม่เกี่ยวข้อง; ทีมขายไม่ต้องเห็นข้อมูลการเงินทั้งหมด
Connectโปรไฟล์สำหรับการจับคู่เฉพาะผู้ที่มีสิทธิ์และตรงเงื่อนไขที่เลือกความสนใจทางเพศลงค้นหาสาธารณะ โปรไฟล์ที่ทำงาน คำแนะนำสินค้า หรือการฝึก AI; ไม่เปิดสถานที่แบบพิกัด

ใช้ account ID เดียวภายใน แต่ใช้ public profile ID และ dating profile ID แยกกัน ป้าย “ยืนยันบัญชี” ต้องบอกว่าตรวจอะไรจริง ไม่เท่ากับรับรองประวัติ ความน่าเชื่อถือ หรือความปลอดภัยของคนคนนั้น แอดมินระบบเข้าข้อมูลส่วนตัวได้เฉพาะเหตุผลและบทบาทที่กำหนดพร้อม audit ไม่ใช่เปิดดูได้ตามตำแหน่ง

ความเป็นผู้ใช้ Panthorium Browser เป็นขอบเขตประสบการณ์ ไม่ใช้ User-Agent เป็นหลักฐานความปลอดภัย ทุก API ตรวจบัญชี สิทธิ์ และบริบทที่เซิร์ฟเวอร์ การซ่อนเมนูไม่ใช่การป้องกันการเข้าถึง

5. การใช้งานตามวัยและความสามารถ

อายุด้านล่างเป็น ข้อเสนอการออกแบบผลิตภัณฑ์ ต้องตรวจตามประเทศที่เปิดให้บริการและนโยบายร้านแอป ไม่ใช่คำรับรองข้อกฎหมาย

กลุ่มรูปแบบที่เสนอ
เด็กอายุต่ำกว่า 13 ปีเริ่มจากพื้นที่ครอบครัว/โรงเรียนแบบปิด รายชื่อที่อนุญาต เนื้อหาที่คัดเลือก การควบคุมผู้ปกครองตามขอบเขตที่เปิดจริง ไม่มีค้นหาคนแปลกหน้า ไลฟ์สาธารณะ หรือหาคู่ หากระบบดูแลเด็กยังไม่พร้อม ให้ปิดโมดูลสังคมสำหรับกลุ่มนี้ก่อน
อายุ 13–17 ปีค่าเริ่มต้นโปรไฟล์เป็นส่วนตัว จำกัดผู้ติดต่อและการกล่าวถึง ปิด DM จากผู้ใหญ่แปลกหน้า ไม่เปิด Connect ไม่แสดงตำแหน่งละเอียด จำกัดการซื้อและขายตามสิทธิ์ผู้ดูแล/ประเทศ
อายุ 18 ปีขึ้นไปเปิดฟังก์ชันสังคมตามการตั้งค่า ส่วน Connect ต้องสมัครใจและผ่านการตรวจคุณสมบัติ ไม่ใช้เพียงปุ่ม “ฉันอายุเกิน 18” เป็นมาตรการทั้งหมด
โหมดอ่านง่ายและช่วยการใช้งานผู้ใช้ทุกวัยเลือกข้อความใหญ่ ปุ่มแตะง่าย ความเร็วเสียง การอ่านรายการทีละข้อ คำบรรยาย และให้ยืนยันผู้รับก่อนส่งเงินหรือข้อมูล ไม่บังคับจากอายุหรือเหมารวมความสามารถ

6. แชท การโทร และการจับคู่ที่เคารพผู้ใช้
  • คำขอแชท: คนที่ยังไม่รู้จักส่งคำขอได้ตามนโยบาย ผู้รับเห็นข้อความเกริ่นสั้น ๆ ก่อนรับ รูป/วิดีโอจากคนแปลกหน้าไม่แสดงทันที ปิดการโทรจนผู้รับยอมรับสิทธิ์การติดต่อ
  • สถานะข้อความ: ร่าง → กำลังส่ง → เซิร์ฟเวอร์รับแล้ว → ส่งถึงอุปกรณ์ → อ่านแล้วเมื่อเปิดอนุญาต การรีเฟรชหรือส่งซ้ำจากเน็ตหลุดไม่สร้างข้อความซ้ำ ข้อความร่างเมื่อออกจากบัญชีต้องไม่รั่วไปบัญชีถัดไป
  • สถานะสาย: เสนอคำเชิญ → กำลังเรียก → รับ/ปฏิเสธ/หมดเวลา → เชื่อมสื่อ → สนทนา → จบ/เชื่อมต่อล้มเหลว รองรับรับสายจากอุปกรณ์เดียว อีกอุปกรณ์หยุดเรียก แจ้งสายไม่ว่างและเวลาห้ามรบกวน
  • เมื่อ Browser อยู่เบื้องหลัง: ออกแบบ push, สายที่ไม่ได้รับ และการกู้สถานะเมื่อกลับเข้าแอปแยกจาก WebSocket หน้าที่เปิดอยู่ ต้องทดสอบ Android/อุปกรณ์จริง ไม่รับประกันว่าเว็บที่ถูกระบบพักหรือปิดแล้วจะดังเหมือนแอปโทรศัพท์ จนกว่า wrapper และการแจ้งเตือนรองรับจริง
  • ความเป็นส่วนตัวของ RTC: สำหรับ Connect และผู้ติดต่อใหม่ เสนอ relay-only เพื่อไม่ให้คู่สนทนาเรียนรู้ IP โดยตรง มีต้นทุน TURN เพิ่ม ต้องแสดงข้อจำกัดเมื่อโครงสร้าง relay ยังไม่พร้อม ไม่แอบลดระดับความเป็นส่วนตัว
  • กล้องและบันทึก: กล้องเริ่มปิด เปิดด้วยการกระทำของผู้ใช้ บันทึก/ถอดเสียงเริ่มปิด ต้องแจ้งทุกฝ่ายและได้รับความยินยอมใหม่เมื่อมีคนเข้าร่วม ปุ่มวางสายหยุด track อุปกรณ์จริงและถอนสิทธิ์ห้อง
  • การเข้ารหัส: ออกแบบ TLS และการเข้ารหัสที่พักข้อมูลเป็นพื้นฐาน หากยังไม่ได้ทำโปรโตคอล E2EE พร้อมจัดการกุญแจหลายอุปกรณ์และตรวจทานอิสระ ต้องไม่โฆษณาว่าแชท/สาย “ปลายทางถึงปลายทาง” เพราะเพียงใช้ HTTPS/WebRTC
  • จับคู่: ผู้ใช้ระบุตัวตนและความสนใจเอง ทั้งสองฝ่ายต้องผ่าน age eligibility และความต้องการที่เข้ากัน ไม่อนุมานเพศหรือรสนิยมจากหน้า เสียง ประวัติซื้อ หรือเครือข่ายเพื่อน ไม่จัดอันดับความน่าดึงดูดด้วยใบหน้า
  • ยุติความสัมพันธ์: ยกเลิกจับคู่หยุดการติดต่อใหม่; บล็อกหยุดการพบเจอ/แชท/โทรตามขอบเขตที่อธิบาย ผู้ใช้รายงานและเลือกแนบหลักฐานได้แม้บล็อกแล้ว ไม่มีการอ่าน/เปิดเผยบันทึกส่วนตัวทั้งหมดให้ผู้ถูกรายงาน
  • พบกันภายนอก: เสนอส่งกำหนดนัดให้ผู้ติดต่อที่ผู้ใช้เลือกเป็นรายครั้ง เตือนเช็กอินได้เมื่อเปิดใช้ ไม่ติดตามตำแหน่งเบื้องหลังหรืออ้างว่าเป็นระบบรับประกันความปลอดภัย

ไลฟ์ผู้ชมจำนวนมากผู้ดำเนินรายการใช้ RTC → bridge/ingest → Live Stream API หรือ media pipeline ที่ทดสอบ → HLS/DASH → GCS/CDNไม่ส่ง peer stream ใหม่จากเครื่องผู้ไลฟ์ให้ผู้ชมทุกคน แยกวงสนทนาหน่วงต่ำออกจากผู้ชม broadcast และแสดงความหน่วงจริง [G3]

การเลือก TURN/SFU หรือเปิด API เพิ่มเป็นงาน deployment ที่ต้องตั้งค่าและทดสอบ ไม่ถือว่าเชื่อมเสร็จเพราะมี Google Cloud อยู่แล้ว ไม่ต้องสร้าง cloud ของตัวเอง ทุกบริการเพิ่มเติมอยู่ในโครงการ/ขอบเขตที่อนุมัติบน Google Cloud ได้

การไลฟ์จาก Browser ส่งสื่อแบบ WebRTC จึงต้องมี bridge ไปเป็น RTMP/SRT ก่อนเข้า Live Stream API ไม่ใช่ให้ Browser ต่อ API นี้แทนสายวิดีโอโดยตรง สำหรับ pilot ขนาดเล็กอาจใช้ SFU egress ออก HLS ไป GCS เมื่อทดสอบแล้ว เพื่อลดการแปลงซ้ำก่อนขยายไป pipeline broadcast เต็มรูปแบบ

แยก social service account และ media buckets ตามหน้าที่ กำหนด least privilege แยก production/staging เช่นเดิม ไม่เปิด GCS เป็น public เพื่อแก้ปัญหาเล่นคลิป และไม่เอาคอนเทนต์องค์กรไปอยู่ bucket สาธารณะ

9. วงจรสื่อและการเพิกถอนสิทธิ์
  1. ตรวจบัญชี สิทธิ์อัปโหลดและพื้นที่คงเหลือ → จองโควตาแบบ transaction พร้อมหมดอายุ
  2. ให้ upload session จำกัด object key อายุและเจ้าของ → อัปโหลดต่อจากเดิมได้เมื่อเครือข่ายขาด
  3. ตรวจขนาด/ชนิดไฟล์จากเนื้อหา ไม่เชื่อนามสกุล → ตรวจ checksum → เก็บกักก่อนเผยแพร่ → ตรวจไฟล์และนโยบายเนื้อหา
  4. ประมวลผลเป็น rendition ตามโควตาและอุปกรณ์ สร้าง thumbnail/caption ที่ต้องมีสิทธิ์เช่นเดียวกับวิดีโอ ไม่มีคลิป “เผยแพร่แล้ว” ทั้งที่ยังเล่นไม่ได้
  5. ตรวจสิทธิ์ตอน publish และตอนออก playback grant ให้ลิงก์อายุสั้นตามบริบท ทุก manifest/segment/thumbnail ของ private media ต้องอยู่ภายใต้เส้นทางที่ป้องกันจริง
  6. เมื่อเปลี่ยนผู้ชม/ลบ/ถูกระงับ ให้ถอน grant หยุดออก token ใหม่ และจัดการ cache/derived media แต่ลิงก์ที่ออกไปแล้วอาจใช้ได้จนหมดอายุ จึงต้องกำหนดหน้าต่าง revocation และทดสอบ; ข้อมูลอ่อนไหวที่ต้องถอนทันทีต้องตรวจสิทธิ์ทุกคำขอแทน cache สาธารณะ
  7. การลบมีงานตาม source, variants, thumbnails, captions, search, CDN และสำเนาสำรองตาม retention พร้อมสถานะติดตาม ไม่แสดงว่าลบทุกแห่งทันทีทั้งที่เพียงซ่อนโพสต์

Public clip ที่ผู้รับดาวน์โหลดหรือบันทึกไปแล้วไม่สามารถรับประกันเรียกคืนได้ การพรีวิว share card และ push notification ต้องใช้ข้อมูลน้อยที่สุด และไม่ใส่เนื้อหาแชท/ข้อมูลหาคู่ลง URL หรือ log

10. ร้านค้า การชำระเงิน และรายได้ของ Panthorium

เริ่มจากหน้าร้าน + สินค้า + แชทที่มีบริบท เพื่อให้ร้านใช้ได้จริงและวัดความสนใจ ก่อนเปิดรับเงินแทนผู้ขาย ต้องทำ seller onboarding, ข้อตกลงผู้ขาย, payment routing/settlement, คืนเงิน, ข้อพิพาทและการกระทบยอดให้ครบ ระบบ Omise ที่มีอยู่ใช้ซื้อสิทธิ์ Panthorium ไม่ใช่ระบบ marketplace หรือ escrow โดยอัตโนมัติ

  • บทบาทร้าน: เจ้าของ, ผู้ดูแลสินค้า, แอดมินตอบลูกค้า, แพ็ก/จัดส่ง, การเงิน; การดูที่อยู่ลูกค้าและการคืนเงินเป็นสิทธิ์แยก
  • ออเดอร์: draft → quoted → reserved → payment pending → paid → processing → shipped → completed; ทางออก cancelled/expired/refund requested/refunded/disputed ค่าชำระสำเร็จมาจาก webhook ที่ตรวจสอบฝั่งเซิร์ฟเวอร์เท่านั้น
  • สินค้าปิดขายแล้วต้องไม่ถูกซื้อจากคลิปเก่าหรือไลฟ์เก่า สต็อกตรวจใหม่ตอนจอง คูปอง/affiliate ใช้ snapshot และตรวจเงื่อนไขเดียวกันทุกช่องทาง
  • แยกบัญชีเงินผู้ขาย รายได้แพลตฟอร์ม เครดิต AI และเครดิตผู้สร้าง ไม่ถือว่าเหรียญในระบบเป็นเงินฝากหรือเส้นทางจ่ายเงินให้ผู้ขาย
  • สินค้าจริงกับสิทธิ์ดิจิทัลต้องแยกเส้นทางซื้อและประเมิน Google Play Payments ตามสินค้าจริงและตลาดที่เปิดใช้ ไม่ใช้ปุ่มนอกระบบเป็นทางหลบกฎ [P4]

ลำดับรายได้ที่เสนอ: เครื่องมือร้านค้า/ผู้สร้างแบบสมาชิกที่มีโควตาชัดเจน → เครื่องมือไลฟ์และจัดการทีมร้าน → ค่าธรรมเนียมธุรกรรมเมื่อรับชำระ/คืนเงิน/จ่ายผู้ขายได้จริง → สมาชิกผู้สร้างและสื่อดิจิทัลเมื่อสิทธิ์กับกฎร้านแอปพร้อม ไม่พึ่งรายได้โฆษณาตั้งแต่เริ่มที่ยังไม่มีฐานผู้ชม และไม่รับประกันรายได้ภายในเดือนนี้

สิทธิ์บล็อก รายงาน ป้องกันการติดต่อ และตั้งความเป็นส่วนตัวต้องใช้ได้โดยไม่ต้องซื้อแพ็กเกจ การแนะนำคู่ไม่ใช้ความเหงาหรือความเปราะบางเพื่อกดดันให้จ่ายเงิน

11. การดูแลชุมชนและความเชื่อถือที่ใช้งานได้

ทุกโพสต์ คลิป สินค้า ไลฟ์ โปรไฟล์ และบทสนทนามีเมนูรายงาน/บล็อก ณ จุดใช้งาน รายงานเข้า case ที่มีสถานะ ผู้รับผิดชอบ เหตุผลการตัดสิน และช่องอุทธรณ์ การลบสื่อมีผลต่อทุกที่อ้างอิง ไม่ปล่อยให้ thumbnail หรือ replay ของเนื้อหาที่ลบยังมองเห็น

ผู้ดูแลไลฟ์หยุดแชท นำผู้ร่วมรายการออก และยุติสตรีมได้ตามบทบาท รายงานเร่งด่วนมีคิวและคนดูแลจริง ต้องมีความสามารถปิดเผยแพร่/อัปโหลด/ไลฟ์แยกส่วนโดยไม่ทำให้ระบบผู้ช่วยส่วนตัวทั้งหมดหยุด

Google Play กำหนด UGC ให้มีข้อกำหนดการใช้งาน การรายงาน การบล็อก และการดูแลต่อเนื่อง; แอป Social/Dating อยู่ภายใต้ Child Safety Standards ซึ่งรวมมาตรฐานสาธารณะ กระบวนการรับและจัดการรายงาน และผู้ติดต่อที่รับผิดชอบ [P2] [P3] ปุ่มรายงานเพียงปุ่มเดียวไม่เท่ากับมีกระบวนการเหล่านี้ครบ

นโยบายเริ่มต้นเสนอชุมชนทั่วไป ไม่มีเนื้อหาทางเพศโจ่งแจ้ง ไม่ออกแบบ random stranger video roulette สิทธิ์หาคู่รองรับความสัมพันธ์ทุกเพศอย่างเท่าเทียม ไม่ใช่โหมดเผยแพร่สื่อทางเพศ การตรวจทานและบังคับใช้ใช้พฤติกรรมและเนื้อหา ไม่ตีตราจากรสนิยมทางเพศ

เรื่องลิขสิทธิ์มีเจ้าของผลงาน/สิทธิ์เผยแพร่ ช่องร้องเรียนและอุทธรณ์ แยกการใช้งานที่อนุญาตออกจากการคัดลอก ไม่อ้างว่ามีระบบเทียบลิขสิทธิ์เทียบเท่า Content ID โดยไม่ได้สร้างและทำข้อตกลงจริง

สื่อจาก AI มีช่องระบุว่าเป็นสื่อสังเคราะห์และเก็บ provenance ที่เกี่ยวข้อง การสวมรอยตัวบุคคลหรือใช้เสียง/ภาพผู้อื่นโดยไม่ได้รับอนุญาตมีประเภทการรายงานเฉพาะ ป้ายแสดงแหล่งที่มาเป็นข้อมูลประกอบ ไม่ใช่คำรับรองว่าเนื้อหานั้นเป็นความจริง

12. ค่าใช้จ่ายและข้อจำกัดที่ต้องควบคุมตั้งแต่วันแรก

ต้นทุนหลักคือพื้นที่และสำเนาวิดีโอ การแปลงไฟล์ ปริมาณข้อมูลส่งถึงผู้ชม TURN/SFU นาทีการโทร เวลาที่ไลฟ์เปิด คำขอฐานข้อมูล และงาน AI ควรวัดแยกตามผู้ใช้ ร้าน ช่อง และรายการไลฟ์ แล้วเทียบกับแพ็กเกจที่ขายจริง

  • เริ่มคุณภาพเล่นอัตโนมัติตามเครือข่าย มีโหมดประหยัดข้อมูล ปิด autoplay ที่ใช้ข้อมูลหนัก ไม่สร้างทุก resolution โดยไม่มีผู้ชมใช้
  • จอง quota ก่อน upload/transcode/เริ่มไลฟ์ จำกัดงานพร้อมกัน มีงบต่อบัญชีและต่อระบบที่ตรวจใน backend ไม่ใช่แค่คำเตือนหน้า UI
  • หยุดห้องไลฟ์และทรัพยากรที่ค้างเมื่อเจ้าของออก เก็บ heartbeat/lease และมี sweeper ตรวจซ้ำ; กำหนดระยะเก็บต้นฉบับ/ร่าง/ไฟล์อัปโหลดไม่สำเร็จแยกกัน
  • สำหรับผู้ชม broadcast ประมาณข้อมูลคร่าว ๆ ด้วย bitrate Mbps × วินาทีที่ดูรวม ÷ 8 เป็น MB แบบฐานสิบ ยังไม่รวม protocol overhead/การดูซ้ำ/สำเนาและงานประมวลผล ใช้วัดจากการใช้งานจริงก่อนตั้งราคา
  • เปิดฟีเจอร์เป็น cohort; เมื่อเกินงบให้หยุดรับงานใหม่อย่างมีข้อความชัดเจน ไม่ตัดการโทรที่กำลังดำเนินอยู่โดยไม่เตือน และไม่ลบข้อมูลผู้ใช้เงียบ ๆ

ตัวเลขราคายังไม่กำหนด เพราะต้องทราบผู้ใช้งานพร้อมกัน นาทีดู/โทร ปริมาณอัปโหลด และบริการ RTC ที่เลือก โควตาที่ประกาศขายต้องเป็นโควตาที่ระบบบังคับได้จริง ไม่ใช้คำว่า unlimited สำหรับสื่อที่มีค่าใช้จ่ายต่อการใช้งาน

13. สิ่งที่มีในโค้ดเดิมและสิ่งที่จะต้องสร้าง
ฐานเดิมที่ตรวจพบสิ่งที่ต้องต่อยอด
middleware/auth.js และ auth repositoryใช้บัญชีและตรวจสถานะปัจจุบันเดิม เพิ่ม public profile, discoverability, age eligibility, consent และ block policy
services/cloudFilesService.jsไฟล์เดิมจำกัด 20 MB และ buffer ทั้งไฟล์ เหมาะกับหน้าที่เดิม แต่ต้องทำ social media pipeline แบบ resumable/async/shared grants ใหม่
services/mediaStudioService.jsใช้สร้างผลงานได้ เพิ่ม explicit publish handoff; ย้ายงานแปลงวิดีโอหนักออกจาก API และสถานะใน process
services/geminiLiveWebSocket.jsเป็นเสียงระหว่างผู้ใช้กับ AI เพิ่ม gateway สำหรับมนุษย์คุยกันแยก; ไม่ส่งสายของสองคนผ่าน Gemini โดยปริยาย
services/omiseBillingService.jsใช้ความรู้เรื่อง webhook/idempotency; marketplace settlement และการเงินผู้ขายต้องพัฒนาเพิ่มแยกจาก subscription
start-menu-ui.js, window manager, voice window catalogเพิ่มหมวด ไอคอนและ opener ที่ตรวจสิทธิ์; voice actions สำหรับแชร์/โทรใช้การยืนยันและบันทึกผล
mobile/android/scripts/prepare-android.jsปัจจุบันมีสิทธิ์ไมโครโฟน ยังต้องเพิ่ม/ทดสอบกล้องและ UX เมื่อปฏิเสธ รวมถึง background/resume จริง
server.js CSP และ database poolเพิ่มเฉพาะ origin ของสื่อ/RTC ที่เลือกจริง จำกัด connection รวมทุก instance และแยก workload เพื่อไม่ทำให้เสียง AI เดิมสะดุด

ยังไม่พบ social graph, peer DM/calls, feed, live commerce หรือ dating service ในโค้ดฐานที่ตรวจ การออกแบบนี้จึงไม่อ้างว่าฟังก์ชันเหล่านั้นใช้งานได้แล้ว

14. ลำดับพัฒนาและหลักฐานก่อนเปิดแต่ละส่วน
ลำดับชิ้นงานที่เปิดใช้ได้หลักฐานที่ต้องผ่าน
A — รากฐานร่วมprofile แยกบริบท, policy/age/consent, media upload ใหม่, block/report, moderation inbox และ usage ledgerบัญชี A อ่านไฟล์/ข้อความ B ไม่ได้; เปลี่ยนสิทธิ์มีผล; logout ไม่รั่วข้ามบัญชี; อัปโหลดไม่ทำ API หน่วยความจำเต็ม
B — วงจรใช้งานแรกCommunity + Watch + Talk แบบข้อความ/ภาพ/คลิป + หน้าร้าน/สินค้า/สอบถาม เหมาะกับ creator และร้านกลุ่มนำร่องอัปโหลด–ประมวลผล–เผยแพร่–แชร์–เปิดตามสิทธิ์ครบ; ส่งซ้ำไม่ซ้ำ; คนถูกบล็อกติดต่อใหม่ไม่ได้; รายงานถูกจัดการจริง
C — สื่อสดโทรเสียง/วิดีโอแบบยอมรับก่อน, live pilot, ผู้ดูแลห้อง, ปักสินค้า, เลือกย้อนหลังทดสอบสองผู้ใช้คนละเครือข่าย/CGNAT, TURN, เน็ตหลุด, permissions, Android background; ตัดอุปกรณ์และหยุดค่าใช้จ่ายหลังจบจริง
D — ซื้อขายครบวงจรชำระ/จ่ายผู้ขาย/คืนเงิน/ข้อพิพาท, สต็อก และคำสั่งซื้อจากคลิป/ไลฟ์ทดสอบ webhook ซ้ำ/สลับลำดับ สต็อกชิ้นสุดท้ายถูกซื้อพร้อมกัน ยอดชำระไม่ตรง คืนเงินและกระทบยอด; กฎร้านแอปตรงกับ build จริง
E — Connectopt-in adult dating, mutual preferences/match, chat/call, pause/unmatch/block และ privacy controlsผู้เยาว์เรียก API ตรงไม่ได้; account อายุต้องสงสัยระงับ eligibility; ข้อมูลหาคู่ไม่ขึ้น search/analytics/push ของบริบทอื่น; บล็อก/ถอน consent มีผลระหว่าง session

งานแต่ละลำดับพัฒนาแยกขนานกันได้ แต่เปิดใช้ตาม readiness ที่พิสูจน์แล้ว ไม่ใช้วันครบกำหนดแทนหลักฐาน การวัดความสำเร็จเริ่มจากคนเผยแพร่ครั้งแรกสำเร็จ คนได้รับคำตอบที่ตั้งใจหา การติดต่อที่ได้รับการยอมรับ การแก้รายงาน และต้นทุนต่อผู้ใช้งานจริง ไม่วัดเพียงเวลาเลื่อนฟีดให้นานที่สุด

รุ่นแรกตัดสิ่งที่ใช้ต้นทุนสูงแต่ยังไม่จำเป็นออก ได้แก่ 4K ทุกคลิป, ไลฟ์ไม่จำกัด, ระบบเหรียญ/ของขวัญซับซ้อน, ฟีดแนะนำอัตโนมัติเต็มรูปแบบ และการสุ่มวิดีโอคอลกับคนแปลกหน้า ส่วนการรายงาน บล็อก สิทธิ์สื่อ และข้อจำกัดอายุเป็นฐานร่วมที่ต้องมี

15. รองรับอนาคตโดยไม่ผูกติดอุปกรณ์

แยก UI ออกจาก action contract และ media transport: actor + context + intent + target + audience + consent + idempotency + result ทำให้คำสั่งจากคีย์บอร์ด เสียง แว่น หรืออุปกรณ์ช่วยการเข้าถึงใช้นโยบายเดียวกัน

ใช้ protocol/schema ที่มี version, adapter สำหรับ RTC/payment/AI/media, ส่งออกข้อมูลในรูปแบบมาตรฐาน, database migration แบบเพิ่มก่อนย้าย และตรวจ rollback เก็บคำอธิบายสิทธิ์กับ provenance ไว้กับข้อมูล สิ่งเหล่านี้ทำให้เปลี่ยนเทคโนโลยีได้ยาวนาน แต่ไม่มีแบบสถาปัตยกรรมใดรับประกันความเข้ากันได้ล่วงหน้า 200 ปี

โหมดไร้จอใช้คำบรรยายสั้น ๆ ตัวเลือกที่ไม่มาก การยืนยันผู้รับ/ผู้ชม และคำสั่งหยุดที่ทำงานได้เสมอ แว่นแสดงบริบทเท่าที่จำเป็น ไม่แสดงข้อความส่วนตัวหรือโปรไฟล์หาคู่ในพื้นที่ที่คนอื่นเห็นโดยไม่ตั้งใจ
