# โครงสร้าง Panthorium

เบราว์เซอร์และ Panthorium Browser โหลดหน้าหลักจาก Express ส่วนการตรวจบัญชี สิทธิ์ของแพ็กเกจ การคำนวณราคา และการบันทึกฉบับอยู่ที่เซิร์ฟเวอร์ โปรไฟล์ notebook production กำหนดให้ Gemini Live ทำงานหน้าบ้านใน `ops/notebook/runtime.py` งานเทียบบรีฟ คำนวณเงิน และจัดคิวข้อเสนอทำในแอปโดยตรง

| ส่วนของระบบ | ความรับผิดชอบ | จุดตรวจ |
| --- | --- | --- |
| หน้าหลักและหน้าสมาชิก | โหลดสคริปต์จากรายการใน `server.js` ใช้แค็ตตาล็อกเดียวกับแพ็กเกจเดิม | ทดสอบหน้าสมาชิกและเส้นทางเปิดผู้ช่วยงาน |
| API และการยืนยันตัวตน | Express ตรวจ access token, session และสิทธิ์ก่อนเรียกบริการ | คำขอที่ผิดรูปแบบ บัญชีแขก และสิทธิ์ข้ามบัญชี |
| ข้อมูลแฟ้มงาน | PostgreSQL เก็บข้อมูลแยกเจ้าของ การเขียนใช้ธุรกรรม เลขฉบับ และรหัสคำสั่งสำหรับลองซ้ำ | ทดสอบคำขอพร้อมกันและลองคำสั่งเดิมซ้ำกับ PostgreSQL |
| สิทธิ์และราคา | เซิร์ฟเวอร์อ่านสมาชิกที่มีผลจาก entitlement service เครื่องมือเสนอราคาคิดเป็นสตางค์ตามราคาที่ผู้ใช้กรอก | เขตสิทธิ์ทั้งสี่ระดับและยอดรวมที่ปัดเศษได้ตรง |
| การปล่อยรุ่น | GitHub CI ตรวจรุ่นก่อนเลื่อน ref ของ notebook จากนั้นตัวควบคุมตรวจรุ่น ฐานข้อมูล ไฟล์ที่จำเป็น และสถานะพร้อมใช้งาน | ตรวจทั้ง candidate และทางเข้าที่ลูกค้าใช้ รองรับการกลับไปรุ่นก่อนหน้า |

## มาตรฐานสำหรับ API ใหม่

ใช้ OpenAPI 3.1 ระบุเส้นทาง สัญญาข้อมูล และรหัสสถานะ ให้การทดสอบส่งคำขอ HTTP จริงและตรวจผลกับ schema การตอบข้อผิดพลาดของงานบรีฟใช้ RFC 9457 และคงรหัสข้อผิดพลาดของ Panthorium เพื่อแสดงคำอธิบายภาษาไทย ตัวอย่างเริ่มต้นได้ที่ [สัญญา API งานบรีฟและการตรวจสถานะ](openapi/work-briefs.json) เว็บให้บริการสัญญานี้ที่ `/api/spec/work-briefs.json`

หน้าฟอร์มใช้องค์ประกอบ HTML ที่มีชื่อกำกับ รองรับคีย์บอร์ด แสดงสถานะเป็นข้อความ และจัดวางสำหรับจอแคบ แนวทางที่ใช้อ้างอิงคือ [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## งานบรีฟและข้อเสนอ

เจ้าของงานตรึงข้อความหรือเลือกไฟล์ที่แนบอยู่กับแฟ้ม ตัวอ่านไฟล์คัดลอกข้อความพร้อมชื่อและค่า SHA-256 ของต้นฉบับ ข้อที่อยู่ในข้อตกลงต้องอ้างบรรทัดในบรีฟฉบับที่เจ้าของงานตรึงไว้ การแก้บรีฟครั้งถัดไปเก็บฉบับที่มีรายการอ้างอิง ราคางานเพิ่มคำนวณจากจำนวนเต็มคูณราคาในหน่วยสตางค์ ผู้ใช้ตรวจข้อความก่อนส่งผ่านช่องทางที่เลือกเอง สถานะลูกค้าตกลงเป็นการบันทึกของเจ้าของงาน ยอดรับเงินจริงอยู่ในกระบวนการเรียกเก็บเงินต่างหาก แพ็กเกจที่หมดอายุยังเปิดอ่านข้อเสนอที่เคยจัดทำไว้ในแฟ้มได้

## การตรวจความพร้อม

`GET /health/live` ตรวจว่ากระบวนการตอบ HTTP ได้ `GET /health/ready` และ `GET /health` ตรวจ dependency ของโหมดที่กำลังใช้งาน ให้ HTTP 503 เมื่อยังรับงานไม่ได้หรือเริ่มปิดระบบ การตรวจที่เข้ามาพร้อมกันใช้ผลตรวจรอบเดียวและจำกัดเวลารอ 5 วินาที `GET /api/health` ใช้ตรวจ revision ในขั้นเผยแพร่ ฐานข้อมูล ไฟล์ และการตั้งค่า AI ที่ production readiness ตรวจดูได้จาก `services/productionIntelligenceService.js`

การกู้ข้อมูลจริง ระยะเวลากู้คืน และจำนวนผู้ใช้พร้อมกันต้องใช้ผลการซ้อมและผลวัดของสภาพแวดล้อมนั้น ดู [รายการตรวจโครงสร้างพื้นฐาน](INFRASTRUCTURE_READINESS.md)
