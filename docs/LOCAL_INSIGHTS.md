# Account statistics and approved security response

The **ความปลอดภัยและสถิติ** window is available to signed-in accounts. Product statistics are off by default. Opting in stores daily per-account feature counters (requests, server errors, denials/rate limits and requests over five seconds), for 30 days. Opting out erases those counters and invalidates aggregate reports in flight. Requests already buffered before a new consent are discarded. Collection is bounded and best effort, not a billing or forensic ledger.

Only current administrators and the verified system owner can access operator reports or invoke analysis. Model input contains allowlisted feature names and numeric aggregates from at least five consenting accounts per feature, plus security event codes/counts. It excludes account IDs, IPs, raw URLs, request bodies, conversations, mail, files and attacker-controlled log text. Aggregate reports expire after seven days. Training and automatic conversation capture remain disabled.

Security rules examine failed logins over 15 minutes and denied/rate-limited HTTP requests over 10 minutes. The scan aggregates the complete time window (up to 200 highest-count IP groups), independently of the dashboard's 500-event sample. An event schedules a scan after one second; a 15-second timer recovers missed events. These are application-event detections, not an antivirus, network IDS, backup verifier or guarantee that all attacks are detected. SQL failures can interrupt monitoring; the dashboard shows its last successful scan.

Alerts go only to the current `admin` account if it is an administrator and the verified owner `rambo4075krub@gmail.com`. A durable outbox deduplicates each incident/severity/recipient, retries publication and notifies on severity escalation. Incidents are grouped by rule family, IP and hour and retained for 30 days. Existing notification history has its separate 90-day retention. Urgent incident warnings bypass quiet hours; other notification preferences remain effective. Actual push delivery requires a live device subscription, OS permission, connectivity and provider availability. No test sends synthetic risk alerts to real recipients.

9B analysis is advisory and tools are disabled. The worker uses the loopback broker and never falls back to paid services. It runs at most once per 30 minutes after a successful report, only with a loaded idle model; unavailable resources defer it. Foreground text/voice preempts the background model request. Existing RAM/VRAM/temperature limits are unchanged. The broker must advertise `backgroundPreemption`; older brokers fail closed. No cold load is performed by background analysis.

The initial executable response is a ten-minute temporary public-IP block. Targets come from detected evidence, never from model prose. Plans show the target, impact, expiry and reversal before confirmation. The existing action ledger binds approval to the account and frozen plan hash; execution rechecks authorization, live evidence, revision, expiration and the stop switch. A database transaction allows only one reviewer to act. Loopback/private/reserved addresses and IPs used recently by either recipient or the approver require manual review. Existing blocks are never overwritten or extended. Reversal deletes only a block still owned by that exact incident. Stop suspends analysis and pending plans, while deterministic alerts continue for the configured authorized owner. Blocks already applied retain their expiry.

Activation: deploy through PR/CI/main, update the host broker with the approved release installer, then run `node ops/enable-local-insights.cjs --enable` using the notebook's existing runtime environment. This resolves both recipients before enabling their in-app/device security alerts; it does not grant OS permission or opt anyone into analytics. Review delivery readiness in notification settings. The owner may stop 9B or reverse incident-owned blocks in the window.

Validation: `node test/local-insights.js`, `TEST_DATABASE_URL=... node test/local-insights-postgres.js`, and `python -m unittest discover -s deploy/hybrid -p 'test_broker.py'`. PostgreSQL tests use a unique isolated schema and delete it afterwards; never substitute a production URL for `TEST_DATABASE_URL`.
